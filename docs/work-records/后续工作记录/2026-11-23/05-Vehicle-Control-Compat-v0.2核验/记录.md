## 10. 失败现象、排查过程、重试与最终状态

- 失败现象 1（静态异常）：v0.2 APK 比 v0.1 少 11 个 base 配置资源文件
  （8 个 `res/color/abc_tint_*.xml` / `abc_btn_colored_*`、`res/layout/abc_alert_dialog_button_bar_material.xml`、
  `res/layout/abc_screen_toolbar.xml`、`res/layout/activity_ainova_build.xml`），但工程 zip 中这 11 个文件
  全部存在。排查：确认缺失的只是 base 配置（`layout-v22`、`layout-v26`、`color-v23` 变体仍在 APK），
  这些文件在 minSdk 26 下通常不会被加载（AppCompat 旧版遗留），因此**推断**对 API 26+ 无功能影响，
  但属于构建管线/工程包不一致，未获构建者记录解释；影响未实测。
- 失败现象 2（方法体等价性误判）：最初用"方法指令字节哈希"比较 v0.1/v0.2，50,708 个同名方法中
  38,617 个哈希不同，看似大规模改动。排查：DEX 指令里的 string/type/method 池索引因新增字符串/类而整体偏移，
  跨包比较必然不同；改用 apktool 反编译后的 smali 文本比较，证明旧代码只改 1 个方法。教训：不能把
  "指令字节相同"当作跨包等价性判据。
- 失败现象 3（资源回读位置）：apktool 解码 APK 时 11 个 base 资源被放进 `unknown/` 目录（无法解码为文本），
  由此一度误判"工程包也缺文件"；改用 zip 条目路径核对后确认工程包含全部 11 个文件。
- 重试：工程包解压（7,965 文件）在 Windows Defender 实时扫描下很慢（约 15 分钟）；rebuilt 时 aapt2
  资源编译又耗时约 20 分钟，第一次构建还因误加 apktool 2.x 的 `--use-aapt2` 参数失败。改为
  `apktool b -j 8`（不带该参数）后成功；未再重试其它构建方式。
- 最终状态：
  - 静态身份/签名/对齐/结构差异/新页集成：**已验证（静态层面）**；
  - 工程包重建一致性：**已验证（unsigned 内容 1,260/1,260 与交付 APK 逐字节相同；签名未复现，因缺私钥）**；
  - 真机安装、启动、页面操作、机器人功能、热点/Wi-Fi：**等待设备或条件**；
  - 11 个 base 资源缺失：重建复现同样的缺失，确认为工程/构建管线确定性行为，非工程包与 APK 不一致；
